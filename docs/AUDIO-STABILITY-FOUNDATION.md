# Audio stability checkpoint 1

Base: c063b7dadbc00f78c713af91f4caac65742e0ac8 (Bushehr V1 source). V2–V10 were generated as browser distributions; they are not contained in this source branch. Do not release this branch over V10 or merge into main without recovering those source changes.

This checkpoint preserves sustained notes on a same-pass severe scheduler stall, skips stale attacks, applies missed releases, and keeps conservative loop-seam recovery. It adds bounded scheduler telemetry and reduces meter/render pressure. It does not make the main-thread scheduler independent of the UI or prove realtime DSP performance. No voice count, preset, master gain, quality or DSP changes.

Next architecture milestone: move transport timing and event dispatch to an audio-clock-owned queue with explicit per-track generations and cancellation (including drums, automation, loop boundaries and recording). Validate 4 tracks with 32/64/128 bars, foreground editing, audio discontinuity measurement, pre-clip peaks, and actual Mac/iPad realtime processing. Do not infer CPU saturation from timer lateness alone.

## Checkpoint 2
Region transactions now report changed track IDs. Their queued drum events are cancelled and their existing scheduling window is refilled without resetting unrelated tracks or the shared transport cursor. Edited tracks can still release their own held voices; this is not the final generation-based audio-thread event architecture. Loop seam and recording regression tests remain required.

## Checkpoint 3
FM and Vector reuse block-constant release coefficients and fixed oscillator pitch, retaining the original per-sample path for glide and FM vibrato. A regression script compares PCM with the exact pre-optimization commit at 44.1/48/96 kHz across notes, voice stealing, glide, pitch bend, modulation and releases. This is a narrow DSP optimization, not a measured CPU reduction on the user's Mac or an independent scheduler.

## Checkpoint 4
Prevent redundant queued full renders when an immediate render already satisfied the same UI request; recording-stat DOM updates are coalesced to animation frames rather than synchronous per-event updates. A real Chromium Web Audio diagnostic uses Bushehr, Tehran, Baku and Yazd with 32 bars and a controlled UI stall. It reports pre-clip/output PCM peaks, silence, non-finite samples and scheduler underruns. Headless PCM is not physical-device audio output; this does not prove the scheduler is independent or that the V10 bundle is fixed. V10 archive is available as a generated distribution without TypeScript source maps; preserve it and recover its source changes before replacing it.

## Checkpoint 5
Four-track diagnostic at 44.1 kHz: normal scheduler underruns 0 over a short 1.60 s measured window; forced 480 ms UI stall produced one underrun of 387.62 ms and skipped six attacks. Pre-clip peaks 1.0414 normal / 1.2290 forced stall; safety clipper output <= 1. This is evidence of scheduler dependency and master overload in the synthetic mix, not a CPU measurement or proof of the user's crackle cause. No automatic gain or limiter change. HQ and Analog engines now cache exact stable-pitch exponentials, with HQ key-track caching; original paths retained for pitch modulation, glide and oriental gestures. Added paired PCM checks at 44.1/48/96 kHz. Scheduler independence and physical device acceptance remain outstanding.

## Checkpoint 6 — independent audio-clock score primitive (experimental)
HQ worklet accepts a bounded, validated, finite packed score of absolute audio sample frames. The render thread drains it directly; no UI callbacks or allocations in drain. Generation checks and reserved negative IDs support explicit cancellation. Existing playback remains unchanged; no production transport calls the experimental protocol. Added deterministic boundary/cancellation tests and a real HQ PCM browser test with five notes scheduled during one second of deliberate main-thread blockage. This is a foundation, not complete Studio independence: integrate per-track arrangement compilation, drum rendering, controller/mono semantics, loop/seek/tempo and transactional edit ownership before activation. Preserve V10; no gain or native DSP change.

## Checkpoint 7 — opt-in Studio finite HQ score integration
The actual Studio transport can prepare and arm finite, note-only, polyphonic HQ tracks. Preparation is silent and acknowledged; IDs never collide with live or prior score voices. Region edits cancel only the edited track's score and return it to the legacy scheduler. Global timeline changes and recording fall back conservatively. This experiment is intentionally disabled by default: loops, controller/mono semantics, live drums, other engines and V10 source reconciliation still need complete integration. Added compiler and actual Studio PCM stall/edit isolation tests. No production release.

## Checkpoint 8 — bounded native drum queue
In the opt-in finite-arrangement mode, eligible note-only drum arrangements retain the original Web Audio synthesis and prequeue at most 1.5 s of events on the audio clock. Dense schedules, edits, parameter changes and global transport changes fall back safely. Cancellation unwinds future choke scheduling newest-first. This protects against short main-thread stalls, not arbitrary stalls, and is not a port of the drum engine into AudioWorklet. The four-track per-track PCM test checks Bushehr + Tehran/Baku/Yazd through a deliberate one-second UI stall, then verifies drum editing leaves the three synth scores armed. Default transport remains unchanged apart from prior general fixes.

## Checkpoint 9 — explicit pre-clip headroom
Separate project-local pre-clip trim (0 to -24 dB) from monitor output volume. Legacy sessions remain unity and no automatic gain or preset modifications are applied. Live mix capture and full mix bounce use the same trim; raw stems intentionally do not. Stereo recent sample-peak warning precedes the clipper, not a true-peak/continuous overload measurement. Browser regression checks -6 dB mix attenuation, live gain and persistence. Existing experimental transport still opt-in; full loop/recording/engine support and V10 reconstruction remain unresolved.

## Checkpoint 10 — repeating audio-clock score
Opt-in note-only HQ scores can repeat on the render clock for loops starting at bar 1, with fractional-period rounding from the original anchor and independent voice IDs each cycle. Native drum buffering uses an independent absolute cursor across loop seams. Added 1000-cycle drift/identity regression and four-track PCM stall across a loop seam. Loops starting later, recording, controller/mono semantics and non-HQ scores remain on the legacy path. No production activation.

The drum density guard now measures the exact sliding-window count, including circular seam clusters, rather than rejecting long sparse arrangements based on total hit count. Added 32-bar loop eligibility regression; no change to synthesis or default scheduler.

## Checkpoint 11 — V10 continuous MIDI source reconciliation (partial)
Reimplemented the continuous absolute-note editor from the saved V10 patch script. Track-wide edits preserve untouched region sources and controller playback, create regions in gaps, and materialize only changed visible regions; undo restores original data. The original region-source editor remains accessible via the scope toggle (important for hidden notes and shared loop sources). No changes to standalone/native engines. This is one V10 feature recovered in TypeScript, not full V2–V10 visual/functional reconstruction or an exact original source recovery. Remaining transport, audio acceptance and design gaps still block release.

## Checkpoint 12 — preserve backing scores during recording
In the opt-in mode, unarmed eligible HQ/drum backing tracks can retain independent playback during MIDI recording from Stop or punch-in. Armed tracks remain on the original capture path; arm changes during recording cancel only the affected score. Count-in, nonzero starts, controller-heavy and mono scores continue using legacy behavior. The browser regression checks replacement recording, backing PCM during a deliberate UI stall and punch-in track isolation. Live MIDI input itself remains main-thread-driven; this is not a claim of complete independent recording/automation support.

## Consolidated acceptance candidate
The normal build keeps legacy defaults. CI also builds a separate audit candidate with the supported audio-clock path enabled by default, exercising the four-track playback, loop, edit and recording acceptance in actual Chromium. A settings control can disable the experiment while stopped. Direct note input, tuning, note-source mutation and audibility changes invalidate affected scores so that unsupported interactions return to the original path. This candidate is not an exact V10 replacement: V10 was distributed as patched JS/CSS without a complete matching source tree, and its full visual parity is not established. Device CPU/dropout acceptance on the user's Mac, unsupported controller/engine semantics, arbitrary loop starts and long drum starvation remain unresolved. No merge or production deployment is authorized.
